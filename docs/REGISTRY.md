# Animal Registry — Cycle 8

**Implements:** [ANIMAL_REGISTRY_DECISION_DOCUMENT_V2.md](ANIMAL_REGISTRY_DECISION_DOCUMENT_V2.md) · **Baseline tag:** `v0.10.0`
**Scope:** animals, parentage, status projection (step 1); lactations and calvings (step 2)

A registry layer holding **real animals from the real farm**, structured as an append-only event log with rebuildable projections over it, living alongside the existing demo tables without touching them.

---

## Context

Everything in this repo before this cycle is either a scripted demo (the 14 seeded buffaloes, their milkings, vendors and deliveries) or camera telemetry (`farm_events`). Neither is a record of anything real about the herd. This cycle adds the first tables whose contents are **facts about actual animals**, and that changes what correctness means: a lost row here cannot be regenerated by re-running a seed.

Three properties follow from that and drive every decision below.

1. **Nothing is ever `UPDATE`d or `DELETE`d in the event log.** Corrections are new events pointing at the events they replace.
2. **Precision is never invented.** A date known only to the month is stored as a month, and says so.
3. **Every derived value is reproducible.** If a projection cannot be rebuilt from the log, it is not derived — it is data that was stored somewhere it does not belong.

---

## The demo / registry fork

Two animal tables now exist in one database, and that is deliberate.

| | `animals` (demo) | `registry_animals` |
|---|---|---|
| Contents | 14 seeded buffaloes | real farm animals |
| Ids | `animal_<8hex>` | `BD-0001` |
| Lifecycle | dropped and recreated by every `seed()` | migration-managed, never dropped |
| Status vocabulary | `AnimalStatus` in `shared/src/types.ts` | `RegistryAnimalStatus` in `registry/types.ts` |
| Read by | the agent's tools | nothing yet — v1 is a service layer |

**The demo tables are fixtures for a scripted demo, not a record of anything.** That is the fact that makes the fork tolerable, and it is why the registry does not simply extend `animals`.

The decisive reason it *cannot* extend `animals`: `resetSchema()` ([db.ts](../server/src/db.ts)) drops and recreates all six demo tables, `seed()` calls it, and the Cycle 3 regression suite calls `seed()` in `beforeEach`. Real animal records in that table would be destroyed by a routine test run. Revision 1 of the decision document proposed separating real from synthetic by putting them in two **database files** selected by an environment variable; that mechanism does not defend against this at all, because the process would be configured correctly and the *command* would be wrong. The table-name split does defend against it, structurally, and costs nothing.

### Where the fork merges

**The tools cycle.** When the agent gets `get_animal` / `get_lactation_history` over the registry, the demo `animals` table becomes redundant: `list_animals`, `search_animals`, `add_animal` and `guardIds()` get repointed, the demo fixtures move to `registry_*` seed data or are deleted, and the regression suite's assertions are rewritten once. Do that as one deliberate cycle, not incrementally.

Until then the fork will widen before it closes. Step 4 (yield) will hit it: `milkings.animal_id` has a foreign key to the demo `animals`, so real yield cannot go there and step 4 gets `registry_milkings`.

Serial format helps here — `BD-0001` cannot collide with `animal_<8hex>`, so if the tables are ever merged the two id spaces stay unambiguous.

### The inconsistency this creates, stated rather than hidden

`farm_events` separates synthetic from real **in-row**, with an `is_synthetic` column. The registry separates by **table name**. Two different answers to the same question in one schema.

The honest position: `farm_events.is_synthetic` exists, and nothing filters on it — the only read is [verify.ts](../server/src/farm/verify.ts)'s assertion that scenario rows *are* synthetic. That flag has never had to separate mixed data, because every row in the table is synthetic. Absence of failure in a column that has never been exercised is not evidence it works — the same shape as the Cycle 5 camera-silence finding.

If `farm_events` ever holds real camera rows alongside synthetic ones, that column has to start being enforced or the table has to split. That is a Cycle 7 problem, not this one.

## Decision 1 — Registry tables are `registry_*` in one database

Six tables, all prefixed, all disjoint from the demo tables:

```
registry_animals            registry_lactations        registry_serial_counter
registry_animal_events      registry_parentage         registry_animal_status
```

The prefix goes on all six, not only the colliding `animals`. The set is the unit: a consistent prefix makes the boundary legible at a glance, lets the isolation guard be a single substring check, and makes any future rename mechanical.

**No registry table has a foreign key to a demo table, and none ever may.** `resetSchema()` drops the demo tables children-first, which is the only reason `foreign_keys = ON` does not abort it; a registry → demo foreign key would start failing that DROP and would couple the two lifecycles.

### The guard (invariant 13)

`resetSchema()`'s DROP list and the `SCHEMA` const are checked — **as source text** — for any `registry_` table. Source text rather than a live database, because the failure mode is someone adding a line to `db.ts`, and that must fail in CI where no database exists.

Both the guard and its ability to fail are tested: `registry.schema.test.ts` corrupts a copy of `db.ts` in three ways and asserts the guard catches each, plus asserts the guard reports *itself* broken if its matchers stop finding what they inspect. A guard that silently stops checking is worse than no guard.

### When two database files come back

Deferred with a concrete trigger, not a vague "later". Revisit when **either**: the database ships to the farm as a deployed artifact, or backup/retention policy differs between real and demo data.

At that point these prerequisites become mandatory and should be built together:

- `import 'dotenv/config'` as the first line of `db.ts`. Four entry points currently lack it — `seed`, `simulate:farm`, `verify:farm`, `verify:classify` — so a `DAIRY_DATASET` in `server/.env` would be invisible to them and `npm run seed` would silently write the wrong file.
- `mkdirSync` before `new Database`, or the process dies at module load on a missing directory.
- A rename runbook covering the `-wal` and `-shm` sidecars (WAL is on).
- The migration runner applied to both files at boot — **already built**, so that list is one shorter.

## Decision 2 — A migration runner, using `PRAGMA user_version`

The repo's first. Until now the schema was two template literals in `db.ts`: `SCHEMA` (dropped and recreated by `resetSchema()`) and `FARM_SCHEMA` (`CREATE TABLE IF NOT EXISTS`, applied at module load).

`IF NOT EXISTS` does **nothing** to a database that already has the table. That is why Cycle 5's four nullable classification columns required every developer to drop a live table by hand ([FARM_MONITOR.md](FARM_MONITOR.md) § "The schema gap"). The registry schema is expected to change at steps 3, 4 and 5, on the one set of tables holding data that cannot be recovered from software. Repeating the `IF NOT EXISTS` pattern would guarantee the same manual drop where it hurts most.

```
registry/schema.ts
  MIGRATIONS: readonly ((db: Db) => void)[]   ordered, append-only
  applyRegistrySchema(db)                     pragmas + migrate, any handle
```

- `PRAGMA user_version` is the marker. **Version 0 means "the schema as it stands at `v0.10.0`"** — the demo tables and `farm_events` are deliberately *not* retrofitted into migration history, because a migration claiming to have created them would be a lie.
- Each migration runs in its own transaction that also bumps the version, so a failure leaves the database at the last good version with nothing half-applied. Verified: `PRAGMA user_version` participates in the transaction and rolls back with the DDL.
- The runner is **global**, not registry-specific. The registry is its first customer; any future cycle appends to `MIGRATIONS`.
- It refuses to run against a `user_version` higher than it knows about — an older build must not touch a newer schema.

**Never reorder, edit, or remove an applied migration.** A database already at version N will not re-run entries below N, so an edit silently produces two different schemas depending on when the database was created.

### Ordering with `FARM_SCHEMA`

`db.ts` applies `FARM_SCHEMA` and then `applyRegistrySchema(db)`. The two are **order-independent** — they touch disjoint tables and `FARM_SCHEMA` is re-appliable — and `registry.schema.test.ts` asserts the reverse order converges to the same tables and the same `user_version`, so the independence is proven rather than assumed.

## Decision 3 — Two event tables; `farm_events` is untouched

`farm_events` is not modified. Animal-life events go in `registry_animal_events`.

The producers differ on every axis a schema cares about — volume (thousands/day vs ~10/week), subject (a camera and a guessed identity vs a known animal), time (an exact machine instant vs a fuzzy local date), recording lag (milliseconds vs weeks, and it matters), provenance (a webhook vs a named person and a paper sheet).

Two repo facts settle it beyond the design argument:

1. **`farm_events` cannot be altered in place at all.** It is `CREATE TABLE IF NOT EXISTS`, so adding `date_precision`, `observed_by`, `source_form` and `supersedes_id` would require a manual drop of a live table on every machine, and would leave a schema with no evolution path. Its two CHECK constraints would also have to widen, against the rule reserving CHECKs for externally-arriving webhook bodies — which animal events are not.
2. **The blast radius on the camera path is zero, not merely small.** Nothing in `server/src/farm/` reads `animals` — no reference to `animals` or `animal_id` exists in any non-test file there. `scoreEvent` scores on zone, event type, confidence, identity and time, never on an animal.

`event_links` and a read-time `getAnimalTimeline` stay deferred: `farm_events.identity` holds people (`employee_1`, `owner`, `unknown_a1`), never animals. There is nothing to link to yet.

## Decision 4 — Source of truth and the projection rule

> `registry_animal_events` is the sole source of truth. `registry_lactations`, `registry_parentage` and `registry_animal_status` are **stored derived state**, reproducible by `registry:rebuild`, and `verify:registry` proves a rebuild reproduces what is stored.

Two consequences, enforced rather than documented:

- **Only `projectStore.ts` writes a projection table.** No other code path touches them, so the only way a projection row can exist is for `projectAnimal()` to have derived it. The calving transaction calls the rebuild for the animals it touched rather than hand-patching rows.
- **Projection tables can be dropped and recreated at any time without data loss.** Literally true here, because `registry_animals` carries **no projection columns at all** — it holds identity (`id`, `name`, `sex`, `species`, `origin`, `post_no`, `tag_no`) and nothing else. Derived state lives entirely in `registry_animal_status`.

`registry_animal_status` deliberately has **no `computed_at` column**. Invariants 0 and 1 compare projection row-sets across rebuilds; a wall-clock stamp would differ on every run and make both unfalsifiable.

### Pure core / DB shell

The same split as `classify.ts` / `classifyStore.ts`, for the same reason:

| Module | Role |
|---|---|
| `project.ts` | **pure** — events in, projections out, no `../db` |
| `events.ts` | **pure** — id generation and payload validation |
| `intervals.ts` | **pure** — the calving-interval metric |
| `invariants.ts` | **pure** — snapshot in, violations out |
| `time.ts` | **pure** — farm-local "today" |
| `store.ts` | DB shell — takes an explicit handle |
| `projectStore.ts` | DB shell — the only projection writer |
| `calving.ts` | DB shell — the transaction |
| `verify.ts` | DB shell — the rebuild-diff, takes a handle |
| `verifyRegistry.ts`, `rebuild.ts` | CLI shells — the only files importing `../db` |

Every function that touches SQLite takes an explicit `db` handle rather than importing the module singleton. That seam is what lets the same code run against the live `dairy.db` and against `new Database(':memory:')` in a test — and it means `db.ts`'s singleton design is untouched.

### `asOf` is a parameter, not a clock read

One status rule depends on the current date: an animal is a `calf` until it is `CALF_MAX_AGE_MONTHS` old. That makes the status projection a function of **time** as well as of the event log.

A hidden `new Date()` inside `project.ts` would make the rebuild non-reproducible and turn invariants 0 and 1 into checks that cannot fail meaningfully — two runs a day apart could legitimately disagree. So `asOf` is passed in, and the consequence is stated rather than hidden:

> **Stored projections go stale as animals age.** A stale row is a real invariant-1 violation, and the correct response is `npm run registry:rebuild`, not a loosened comparison.

`verify:registry` prints that diagnosis when invariant 1 fires, so "stale" is distinguishable from "wrong".

## Decision 5 — Identifiers

### Animal serial: `BD-0001`

Permanent, never reused. Allocated from `registry_serial_counter` **inside the caller's transaction**, so a rolled-back calving does not burn a number. Gaps are acceptable and expected; reuse is not — which is why the counter is a high-water mark and never `MAX(id) + 1`.

Zero-padded to four digits so lexical sort matches numeric sort. Not derived from post position, ear tag, name or species; those all change. `post_no` and `tag_no` are nullable **attributes**, not identity.

### Event id: `aevt_` + a full `randomUUID()`

**The repo's 8-character convention is deliberately not followed here.** Nine sites use `<prefix>_${randomUUID().slice(0, 8)}` — `animal_`, `milking_`, `health_`, `vendor_`, `delivery_`, `farm_event_`, `ds_`. Eight hex characters is 32 bits: a birthday collision around 77k rows, with non-trivial risk far below that.

That matters more here than anywhere else in the repo, because the lactation id is derived from a calving event id and step 4's yield rows will carry it as a foreign key. A collision would silently point yield at the wrong lactation — the exact failure the id-stability decision exists to prevent, reintroduced through the id format instead of the numbering scheme.

No ULID or UUIDv7 dependency is added, and **no sortability is claimed**: creation order is recoverable from `recorded_at`, which is `NOT NULL` and exact.

### Lactation id: `lact_` + the calving event's UUID

Not `<animal>-L<n>`. A sequence-encoded id renumbers every later lactation for an animal the moment an earlier calving is discovered during backfill — which will happen — and any yield row pointing at the old id would then point at the wrong lactation, silently.

Stability comes from deriving the id from an **immutable event**, not from the id format. The display sequence number ("3rd lactation") is computed at read time, where being wrong is visible and harmless.

### Canonical ordering

Wherever event order matters — the rebuild above all:

```sql
ORDER BY occurred_on, COALESCE(occurred_time, '00:00'), recorded_at, id
```

Untimed events sort before timed ones on the same day. Arbitrary, but **stable across rebuilds**, which is the property that matters. `compareEvents()` in `project.ts` implements the same order for the pure core, and a test asserts the two agree on real rows — the one place the core and the query could silently diverge.

## Decision 6 — Time, precision and provenance

### Three times, three columns

| Column | Meaning |
|---|---|
| `occurred_on` | farm-local calendar date, `YYYY-MM-DD` |
| `occurred_time` | farm-local `HH:MM`, **nullable** — present when known |
| `recorded_at` | exact UTC instant of transcription, always present |

Do not collapse the first two into one timestamp with a qualifier. That forces you to invent an hour for a date known only to the month, and the invented hour reads as real to everything downstream. **Nullable time makes "unknown" the actual stored value.**

**Farm-local dates, not UTC instants — do not "fix" this.** `FARM_TZ` is `Asia/Karachi`, Pakistan does not observe DST, and the offset has been fixed for the entire period any record covers, so local date ordering is total and unambiguous. Every operational fact on the farm — the 05:00/12:00/17:00/22:00 rounds, AM/PM milking, the daily sheet — is expressed in local days. Converting to UTC would move the 22:00 round onto the previous day and make every sheet reconciliation a puzzle.

`FARM_TZ` is duplicated in `registry/time.ts` rather than imported from `farm/classify.ts`. That module's subject is camera events and people, and its DB-freedom is a load-bearing property asserted by its own test; importing it for one string would couple the registry to the Farm Monitor classifier. Extracting a genuinely shared constants module is a separate small change, and `FARM_TZ` is the only constant that would qualify for it.

### `date_precision`

`day` | `month` | `year` | `estimated`. **`NOT NULL` with no default** — a default is how `day` gets applied to a guess.

- `month` → stored as the **1st** of that month. `year` → stored as **January 1**.
- `estimated` is deliberately unconstrained beyond being a valid date: it means even the year is inferred, so no convention would mean anything.
- `occurred_time` must be `NULL` unless precision is `day`. There is no such thing as knowing the hour but not the day.

These are enforced in **three layers**, deliberately: schema CHECK constraints (catch it in any process, including a hand-written `INSERT`), `assertDatePrecision()` at the write boundary (catches it with a readable message), and invariants 11/12 (catch historical rows written before a rule existed).

Surface precision wherever a date is displayed — "March 2024 (month)", "~2021 (estimated)". Never a bare date.

### Provenance — four columns on every event

`source_form` (`daily_herd_sheet` | `cycle_card` | `direct_entry` | `import` | `recall`), `source_ref`, `observed_by` (nullable — nobody observed a purchase record), `recorded_by` (`NOT NULL`).

**`recall` is first-class, not a fallback.** Most of the step-2 backfill will be `recall` at `month` precision or worse. If recall rows are indistinguishable from sheet rows, the first calving-interval number is unfalsifiable.

### Corrections

`supersedes_id`, nullable, self-referencing, with a **partial unique index** so two events cannot claim to replace the same one — which would make the correction chain ambiguous. Projections ignore superseded events; chains resolve to the last event.

**A calving date correction is a *paired* correction — and sometimes a triple.** The calving on the dam and the birth on the calf are the same physical fact seen from two animals, so superseding only one leaves the two dates divergent. Invariant 6 catches that, and it is the realistic mistake: the correction feels complete because the dam's record now reads right, while the calf's stale birth date sits on a different animal's timeline where nobody is looking.

When the outcome was `stillborn` or `died_within_24h` there is a **third** event at the same date — the calf's `departure` — and moving only two leaves the calf departed before it was born (invariants 4 and 5 both fire).

Do not do this by hand. `correctCalving()` and `npm run registry:correct-calving` write every half in one transaction; see Decision 9.

## Decision 7 — Append-only, and the pragma it depends on

The repo's **first triggers**:

```sql
CREATE TRIGGER registry_animal_events_no_update BEFORE UPDATE ...
CREATE TRIGGER registry_animal_events_no_delete BEFORE DELETE ...
```

**The triggers alone are not sufficient, and this is the subtle part.** SQLite skips DELETE triggers for the implicit delete inside `INSERT OR REPLACE` unless `PRAGMA recursive_triggers` is ON, and it defaults to **OFF**. Measured, not assumed: with the pragma off, `INSERT OR REPLACE INTO registry_animal_events` silently overwrites a row and fires neither trigger. The append-only guarantee is one keyword away from being false.

So `applyRegistrySchema()` sets it, and `registry.schema.test.ts` proves both directions — that `INSERT OR REPLACE` is rejected, **and**, as a negative control, that with the pragma off the same statement succeeds and the row is silently replaced. If a future refactor drops `applyRegistryPragmas()`, the first test fails and the second explains why.

### The guarantee is PER-CONNECTION, not per-database

This is the most important caveat in the document, so it gets its own heading.

`recursive_triggers` is a **connection** pragma. The triggers live in the database file; the setting that makes them cover `INSERT OR REPLACE` lives in the handle. So the append-only guarantee travels with the connection:

| How you open it | Append-only holds? |
|---|---|
| `import { db } from '../db'` | **yes** — `applyRegistrySchema()` set and asserted it |
| `applyRegistrySchema(new Database(...))` | **yes** |
| `sqlite3 server/dairy.db` | **NO** — `INSERT OR REPLACE` silently overwrites |
| a script calling `new Database()` directly | **NO** |

better-sqlite3 defaults `foreign_keys` ON but `recursive_triggers` **OFF**, so a bare handle loses exactly the setting that matters and keeps the one that is easy to notice.

Two defences, since the database cannot defend itself here:

1. **`assertRegistryPragmas(db)` reads both pragmas back and throws**, and `applyRegistrySchema()` calls it — so a process whose connection lost the setting fails at import rather than mutating an event much later. Setting a pragma and never reading it back is how that becomes invisible. A test asserts the wiring, and asserts a bare handle fails.
2. **Anything that touches registry tables must go through `applyRegistrySchema()`.** If you need a one-off connection, call it. Do not hand-edit registry rows with the `sqlite3` CLI — corrections are events.

(`foreign_keys` is asserted too, even though the library default is currently correct, because depending on a library default for a correctness property is how it breaks in a major version bump.)

`DROP TABLE` still bypasses the triggers regardless of pragmas. Nothing at the SQL level can prevent that; invariant 13 is what guards it — and the drop-and-re-migrate path is the sanctioned way to reset a registry that only ever held throwaway data.

## Decision 8 — Event taxonomy and hand-rolled validation

Six live types: `birth`, `acquired`, `calving`, `dry_off`, `departure`, `note`.

Ten **reserved** types, named so the taxonomy is designed once rather than accreted, and **rejected** by the write boundary rather than accepted with a loose payload: `heat_observed`, `insemination`, `pregnancy_check`, `abortion`, `treatment`, `vet_visit`, `null_observation`, `milking`, `weight`, `body_condition`.

**No validation library was added.** The repo has no Zod and no equivalent; boundary validation today is `guardIds()` plus `String(args.x)` coercion, with JSON-Schema enums enforced by the model rather than by code. Six payload shapes is less code than the dependency would be, and adding one is a repo-wide decision rather than a registry one. `assertEventPayload(type, payload)` in `events.ts` is exhaustive over the discriminated union, with a compile-time exhaustiveness check.

It also **rejects unknown payload keys**. Not pedantry: a typo'd `calf_sexe` would otherwise be stored as JSON, read back as `undefined` by the projection, and produce a wrong derived value with no error anywhere — the same class of silent failure the no-default-precision rule exists to prevent.

Payloads are stored as JSON TEXT with **sorted keys**, so two logically identical payloads serialize identically and key order never reads as a change in a diff.

**Origin invariant:** exactly one `birth` or `acquired` per animal, and no other event except `note` dated before it.

## Decision 9 — The calving transaction

One function, one `BEGIN IMMEDIATE` transaction, all-or-nothing. The most important code in the cycle, because the failure it prevents — orphaned calves and a pedigree of disconnected nodes — surfaces much later and **cannot be repaired from the data**. A calf inserted without its birth event has no dam, and nothing in the log says who it was.

```
1. Validate    dam exists, is female, no departure on/before this date,
               no existing calving within DOUBLE_ENTRY_WINDOW_DAYS
2. Allocate    the next serial, inside this transaction
3. Insert      the calf's registry_animals row, origin = 'born_on_farm'
4. Insert      the calving event on the dam
5. Insert      the birth event on the calf — SAME date, SAME precision
6. Rebuild     projections for dam and calf
```

Step 5's "same date, same precision" is not a nicety. These are the same physical fact seen from two animals; if their dates can diverge, the timeline lies.

**Stillbirth.** `stillborn` and `died_within_24h` still perform steps 2–5, plus a `departure` event with reason `died` on the calf. A stillbirth opens a lactation and counts toward parity and toward the calving interval, so the calf must exist as a node in the graph. Suppressing it would corrupt the one metric this cycle exists to produce.

**Double entry.** The real risk during a recall-based backfill is the same remembered calving arriving from two sheets. A calving within 60 days of an existing one is refused with an explanatory error and requires an explicit `allow_near_duplicate` — never silently accepted, and never silently rejected either.

### The atomicity proof

`recordCalving` takes a **test-only** `__faultAfterStep` parameter, and `registry.calving.test.ts` uses it to prove that a forced failure after each of the six steps leaves zero rows written — animals, events, lactations, parentage **and the serial counter**.

It exists because steps 4, 5 and 6 have no natural failure mode a test can trigger from outside without corrupting the schema, and "we believe it is atomic" is exactly the claim that should not be taken on trust for the one transaction whose failure cannot be repaired.

### Correcting a calving date

`correctCalving()` / `npm run registry:correct-calving`. Same shape as recording: one `BEGIN IMMEDIATE` transaction, the same validation, per-step fault injection proving atomicity.

```
1. Validate    the event exists, is a calving, is NOT already superseded,
               the calf's birth event is the matching one, no departure on/before
               the new date, no other calving within the double-entry window
2. Supersede   the calving, on the dam            -> new date + precision
3. Supersede   the birth, on the calf             -> same new date + precision,
                                                     re-pointed at the NEW calving
4. Supersede   the calf's departure, if any       -> only when the outcome was not
                                                     `live` AND its date matches
5. Rebuild     projections for dam and calf
```

**Why this is an API and not two `appendEvent()` calls.** Invariant 6 catches a half-applied correction — but only afterwards, on the next verification run. That is the wrong place, because this is the single most likely correction during a recall backfill (a remembered date sharpens on a second telling) and the half-applied version *feels complete*. So the pairing is an API guarantee, the way the calf's existence is an API guarantee in `recordCalving`.

**Step 4 was found by a test, not by review.** The first version of this API moved the pair and left a stillborn calf's `departure` on the old date, so the calf departed before it was born and invariants 4 and 5 both fired. The departure is matched by **date**, not merely by existence: a calf that lived and was sold two years later has a departure that is a separate fact and must not be silently re-dated.

**Correcting a correction** extends the chain at its end. Passing an already-superseded event id is refused, with the replacement named — only one event may supersede a given event (partial unique index), so guessing which end was meant would be worse than refusing.

The calf's identity and the outcome are **not** correctable here: they are what the calf's animal row and its departure event were built from, and moving them would desynchronise records this API cannot reach.

### Closing the previous lactation

- A `dry_off` between two calvings → the lactation ended there, `end_reason = 'dry_off'`.
- No `dry_off` → closed at the next calving date, `end_reason = 'inferred_at_next_calving'`.

**The second case never rejects the calving.** Backfilled history routinely has calving dates and no dry-off dates, and rejecting would force the operator to invent a dry-off date — inventing precision to satisfy a constraint. The marker records that the boundary is a **derivation, not an observation**, and is available to anything that later cares about dry-period length.

A `departure` deliberately does **not** close an open lactation: we do not know the animal dried off, and inventing an end date would be the same dishonesty. Status reports `departed` regardless.

## Decision 10 — Status projection

`RegistryAnimalStatus` is defined in `registry/types.ts`. It does **not** extend or modify `AnimalStatus` in `shared/src/types.ts`, and it does not touch the two tool `input_schema` enums — those belong to the demo domain and changing them would be a breaking change to tool schemas for no benefit.

Where the vocabularies can agree at zero cost they do: **`lactating`, not `milking`.** Gratuitous divergence in a small codebase is a tax paid at every future read.

Rules, in order, first match wins:

| | Status | Condition |
|---|---|---|
| 1 | `departed` | a `departure` event exists. Terminal. |
| 2 | `calf` | birth date known and age < `CALF_MAX_AGE_MONTHS` |
| 3 | `lactating` | parity ≥ 1 and an open lactation exists |
| 4 | `dry` | parity ≥ 1 and no open lactation |
| 5 | `heifer` | female, parity 0 |
| 6 | `male` | male, parity 0 |

`parity` = count of non-superseded `calving` events.

**If the birth date is unknown, rule 2 cannot fire** and the animal falls through to `heifer`/`male` even if it is visibly a calf. That is a documented consequence, not a bug: the fix is to enter an *estimated* birth date, which the precision qualifier makes safe to do.

`pregnant` is deliberately absent — it requires breeding events, which are step 5. At step 5 it gets added and the two vocabularies converge except for `heifer`, `male` and `departed`.

### Where the calf threshold lives

`CALF_MAX_AGE_MONTHS = 12` sits at the top of `registry/project.ts`, next to the rules that consume it, marked provisional and awaiting the farm's own usage.

**Not** alongside `FARM_TZ` / `WORK_HOURS` / `RESTRICTED_ZONES` — there is no shared constants module in this repo. Those three are exports of `farm/classify.ts`, whose subject is cameras and people. The convention the repo actually has is a named, exported, commented constant at the top of the module that owns the rule, with the comment stating the value's origin and whether it is provisional — which is what this is.

## Entry points

There is exactly one way to get data in: the CLI. There is **no HTTP route, no agent tool, and no UI** — agent tools are deferred to the tools cycle, and a UI is a cycle of its own. Every command follows the repo convention: `tsx`, hand-parsed `--flag=value` from `process.argv.slice(2)`, a `USAGE` string, and a `require.main === module` guard.

**Six commands: four that write herd data, plus the rebuild and the verifier.**

| Command | Writes |
|---|---|
| `registry:add` | one `acquired` animal + its origin event |
| `registry:calve` | a calving: dam event, calf (minted **or linked**), birth event, parentage, lactation |
| `registry:correct-calving` | a paired (or triple) date correction |
| `registry:event` | `dry_off` \| `departure` \| `note` on an existing animal |
| `registry:rebuild` | projection tables only, from the event log |
| `verify:registry` | nothing |

```bash
# pass one -- the animals that arrived from elsewhere
npm run registry:add -w server -- --sex=female --name=Noor \
  --acquired-on=2019-01-01 --precision=year \
  --birth-on=2017-01-01 --birth-precision=year \
  --source-form=recall --recorded-by=adnan

# pass two -- calvings, OLDEST FIRST, so each calf exists before anything refers to it
npm run registry:calve -w server -- --dam=BD-0001 --on=2023-04-01 --precision=month \
  --calf-sex=female --outcome=live --source-form=recall --recorded-by=adnan

npm run registry:event -w server -- --animal=BD-0001 --type=dry_off \
  --on=2024-01-01 --precision=month --source-form=recall --recorded-by=adnan

npm run registry:correct-calving -w server -- --event=aevt_... \
  --on=2023-05-01 --precision=month --source-form=recall --recorded-by=adnan
```

Every command takes `--help`.

### What the CLI refuses to do

The blocking rules of §11 are enforced by the argument parser, not by a note in a document:

- **`--precision` is required on every date-bearing command.** A missing one is an error, and the message teaches the fix rather than just reporting the omission — because this is the refusal an operator hits most often, and the useful answer to "I don't know the exact date" is `--precision=year` or `=estimated`.
- **`--birth-on` without `--birth-precision` is refused.** A birth date is exactly where `day` would be invented.
- **`--source-form` and `--recorded-by` are required.** Defaulting `source_form` to `recall` would be safe in the honesty direction but would silently label a sheet-transcribed event as remembered, and the whole point of the column is that the two are distinguishable.
- **Unknown flags are rejected.** `--precison=year` must not fall through to "precision missing".
- **Each command refuses what belongs to another and names it.** `registry:event --type=calving` points at `registry:calve`; `--type=acquired` points at `registry:add`; the ten reserved types are refused with the cycle they belong to.

### Link mode — the two-pass reconciliation

`registry:calve --calf=BD-0002` attaches a calving to an animal that **already exists** instead of minting one.

This is not an optional convenience; without it the two-pass backfill has a hole that eats real records. Pass one enters every animal it can, and a farm-born animal whose dam is still in the herd **must** be entered as `acquired` there, because pass one has no calvings yet. Pass two then records the dam's calving — and mints a *duplicate* of an animal already in the registry. Duplicate animal, duplicate origin event, and nothing able to repair either.

In link mode the calf's `acquired` origin is **superseded by a `birth`**, and `registry_animals.origin` is promoted to `born_on_farm`. No serial is allocated. Its birth date becomes the calving date at the calving's precision, replacing whatever the `acquired` event estimated — usually an improvement, and always worth reading in the command's output.

This is **the only supersession in the schema that changes an event's type**, so it needed a narrow exception to invariant 9. The reverse (`acquired` superseding a `birth`) is deliberately still rejected: a birth event is referenced by a calving on the dam, so superseding it away would leave that calving naming a calf with no birth event, which invariant 6 rejects and no further event could repair.

The projection needed no change — `effectiveEvents()` removes the superseded `acquired` before `findOrigin()` sees it, so invariants 3, 4 and 7 all hold across the promotion. That was verified before the mode was built, not after.

Link mode refuses: an unknown animal (it will not silently mint one instead), an animal that already has a birth event, a sex disagreement, an animal being its own calf, a non-`live` outcome (a calf that did not live would not have been entered separately), and an animal with history predating the proposed birth date.

**Procedure vs safety net.** The correct procedure is still strict ordering: use `registry:add` only for animals with no dam who will ever be in the registry, and let everything farm-born be created by its dam's calving, oldest first. Link mode exists because that procedure is unforgiving and one animal entered in the wrong pass would otherwise leave you stuck.

`registry:add` handles **`acquired` only**. A `born_on_farm` animal is created *by* the calving that produced it, in the same transaction that allocates its serial and links its dam — so letting `registry:add` mint one would produce a calf with no dam edge and no calving on any dam, which nothing could repair because no event would say who the dam was. The two-pass backfill order is therefore enforced by which command exists, not by a note.

`registry:event` also guards the terminal-departure rule up front: writing anything but a `note` after a departure is refused with `--allow-after-departure` offered for the genuine out-of-order case, so invariant 5 is not the first place an operator learns about it.

## Verification

**Both a test and a script**, because the two callers need different data:

- **`registry.invariants.test.ts` + `registry.verify.test.ts`** — `:memory:` fixtures, in CI, on every push. Proves the **logic**.
- **`npm run verify:registry -w server`** — the live `dairy.db`. Proves the **data**, which CI will never have.

Both call the same functions in `invariants.ts` and `verify.ts`, so there is one definition of each rule and two ways to reach it.

Unlike `verify:farm` and `verify:classify`, this needs **no running server** — there is no webhook to replay through. That is precisely why the sibling test exists: the stated reason those two are scripts rather than tests ("they need a live server") does not apply here, so the logic would otherwise never run in CI.

### How `npm test` finds these tests

The test script **enumerates its directories** rather than globbing:

```
tsx --test src/*.test.ts src/farm/*.test.ts src/registry/*.test.ts src/tools/*.test.ts
```

It used to be `src/**/*.test.ts`, unquoted. npm runs scripts through `sh`, where `**` is **not** globstar, so that expanded to exactly two levels — which correctly excluded `src/agent/__tests__/regression*.test.ts`, but only by accident of shell semantics. The accident cut both ways: a test placed one level deeper would never run and would report nothing, while quoting the glob to "fix" it hands globbing to node, which *does* recurse and pulls in the three regression files. Those import `../db` at module level and, without an API key, emit `ok N … # SKIP` — which the TAP summary counts as **passing**. CI would report green for a suite that never executed.

node 22 has no `--test-exclude-pattern`; `--test-name-pattern` and `--test-skip-pattern` filter by test *name* and still load the file, so neither solves it.

So the directories are listed, and `src/testWiring.test.ts` asserts the listing is complete: every `*.test.ts` under `src/` is either matched by a pattern in the script or on an `EXCLUDED` list **with a reason**, no excluded file sits in a covered directory, every excluded file still exists, every excluded file is reachable through a `test:regression:*` script, and the script does not use `**` again. Both silent-failure modes — a new directory nobody added, and a regression file drifting into a covered directory — are now loud.

### Invariants

| # | Check |
|---|---|
| 0 | Rebuilding twice produces identical projection row-sets |
| 1 | A rebuild into a fresh database reproduces what is stored |
| 2 | Lactation ids are unchanged across rebuild |
| 3 | Exactly one origin event per animal |
| 4 | No event except `note` dated before its animal's origin, allowing for precision |
| 5 | No event except `note` dated after a `departure` |
| 6 | Every `calving` names an existing `calf_id` with `origin = 'born_on_farm'`, a `birth` event of the same date, precision and sex, and a matching back-reference |
| 7 | Every `born_on_farm` animal has a `dam` parentage edge |
| 8 | No animal has two open lactations; every lactation id derives from its opening calving |
| 9 | No superseded event contributes to any projection |
| 10 | No duplicate serials; counter ≥ max issued |
| 11 | `month` rows dated the 1st; `year` rows dated Jan 1 |
| 12 | `occurred_time` null wherever precision ≠ `day` |
| 13 | `resetSchema()`'s DROP list and `SCHEMA` contain no `registry_` table |

**Invariant 1 is a multiset comparison under a canonical row key, not a byte comparison.** SQLite files differ in page layout, freelists and WAL state for identical content, so a file hash would fail for reasons that mean nothing. This is the same approach [verify.ts](../server/src/farm/verify.ts) already uses for farm events.

**Every invariant is proven able to fail.** `registry.invariants.test.ts` corrupts a fixture specifically to break each one, and a meta-test asserts that every snapshot-level invariant is demonstrably reachable — so a check added to `checkSnapshot()` without a corruption fixture fails the suite. Without that, an invariant that can never fire would pass every clean fixture forever while protecting nothing.

**"Allowing for precision"** (invariants 4 and 5) means comparison at the coarser of the two grains: a `month`-precision event stored on the 1st is not "before" an origin dated the 14th of the same month, because the day was never known. An `estimated` date is not comparable at all.

### The precision histogram — not an assertion

`verify:registry` prints event counts by `source_form` × `date_precision`.

This **replaces** the decision document's original "no fabricated exact dates" checkbox, which is not machine-checkable. Invariants 11 and 12 catch *inconsistent* precision; nothing can catch *dishonest* precision, because that is a claim about the world. A backfill that comes out 90% `day`-precision `recall` is the signal worth acting on, and only the histogram shows it. **Read it; do not assert on it.**

### On an empty registry

Every invariant passes vacuously when there are no animals. `verify:registry` says so explicitly in its output, so nobody mistakes a green run against an empty database for evidence — and a test asserts that vacuity, so the property is documented in code as well as prose.

## The one metric: calving interval

Consecutive `calving` events per animal, ordered by `occurred_on`, interval in days.

- **`measured`** — both endpoints are `date_precision = 'day'`
- **`approximate`** — either endpoint is `month`, `year` or `estimated`

**Reported separately, with counts, never averaged together.** An approximate interval from two month-precision calvings carries roughly ±60 days of uncertainty — larger than the difference between a good interval and a bad one. Blending produces a number that looks precise and means nothing.

`summarise()` takes one quality class at a time and the report exposes both, so there is no overload that could be handed a mixed list. An empty class reports `null` rather than `0`, so it cannot be charted as a value.

The sample-size caveat travels **with** the numbers as a field on the report, not as a comment: five or six milking animals is a case series, not a dataset, and any consumer rendering the mean without it is misrepresenting the sample. Making it a field means a caller has to actively drop it.

## Backfill policy

Blocking rules:

- **Precision is never defaulted.** A missing precision is an error, not `day`.
- **`source_form = 'recall'`** for anything reconstructed from memory. `recorded_by` is whoever remembered it; `observed_by` is null unless they saw it.
- **Do not enter a date you do not have.** `estimated 2021` beats a fabricated `2021-04-12`, because only the first can be corrected without someone first discovering it was wrong.
- **Two passes.** Animals with origin events first; then calvings, oldest first, so `recordCalving` creates farm-born calves that pass one may already have entered as `acquired`. Correct the overlap by **superseding event**, never by delete-and-re-add.
- ~20 animals and 10–20 historical calvings is small enough to enter by hand and check by eye. Do that once, carefully, rather than building an importer.

## Known fidelity gaps

- **The registry is empty.** The schema, transaction, projections, entry points and verification are built and tested; no real animal has been entered, because the herd list does not exist yet. Every `verify:registry` run against the live database therefore passes vacuously. The full path — add, calve, correct, dry off, verify — has been exercised end to end against the live database with throwaway data, which was then removed by dropping the registry tables and letting the migration recreate them.
- **The append-only guarantee is per-connection, not per-database.** See Decision 7. A `sqlite3` CLI session can bypass it; the boot assertion protects the application's own handle only.
- **`registry:add` cannot record an animal's dam.** An acquired animal gets no parentage edges, so a bought-in animal whose dam is known on the farm cannot have that edge asserted yet. The `certainty` column exists for it; nothing writes it.
- **There is no way to correct a non-calving event through a command.** `registry:event` appends; superseding a `dry_off`, `departure` or `note` requires calling `appendEvent()` with `supersedes_id` directly. Only the calving pair, the one that is near-certain during a backfill, has a first-class correction API. (`acquired` is the exception: link mode supersedes it, though only into a `birth`.)

  **The concrete instance that will bite: a calf recorded as stillborn that actually lived.** The two directions are not symmetric.

  | Correction | Possible today? |
  |---|---|
  | live → stillborn/died | **yes** — `registry:event --type=departure --reason=died` on the calf |
  | stillborn/died → live | **no** — needs the calf's `departure` superseded, and nothing can do that |

  The reverse direction needs two supersessions: the calving payload's `outcome`, and the `departure` event `recordCalving` wrote on the calf. `correctCalving` deliberately refuses to touch `outcome` (it is what the calf's animal row and departure were built from), and no command supersedes a departure. So a calf wrongly recorded as stillborn stays departed, and its status stays `departed`, until a `correctOutcome()` exists. Worth building before the backfill if the herd history has any uncertainty about which calves survived; the direction that matters more during entry — discovering a calf died — works today.

- **Correcting a calving date moves a same-day departure with it, by design.** `correctCalving` matches the calf's departure by **date**, and a bull calf sold on the day of birth has a same-day departure. So re-dating the calving re-dates the sale.

  That is right far more often than it is wrong — the two facts are the same day *because* they are tied to the birth, and leaving the sale behind would put it before the animal existed (invariant 4). But it is a consequence rather than an intention: if a same-day departure was genuinely independent of the birth date, the correction will move it anyway and the fix is a further superseding `departure` — which, per the gap above, no command can currently write. Read the command's output: it names every event it superseded.
- **`CALF_MAX_AGE_MONTHS = 12` is provisional** and has no farm evidence behind it — it is awaiting confirmation of how the farm actually talks about the animals.
- **`DOUBLE_ENTRY_WINDOW_DAYS = 60` is provisional.** It is reasoned from a buffalo's 400+ day calving interval, not measured.
- **Status goes stale as animals age.** A consequence of the `calf` rule depending on the current date. The fix is a rebuild; `verify:registry` says so when invariant 1 fires.
- **Parentage `certainty` is always `known` in this cycle**, because the only producer is the calving transaction. The column exists so the backfill can assert an uncertain edge without a schema change.
- **An `acquired` animal gets no parentage edges.** We did not witness its birth, and a fabricated `unknown` edge would add a row asserting nothing.
- **Registry status words are not dispatcher keywords.** `heifer`, `male` and `departed` are absent from `DAIRY_KEYWORDS` in [dispatch.ts](../server/src/agent/dispatch.ts). Harmless now (registry tools are deferred), but a question phrased with them would not route to the dairy agent — fix it in the tools cycle.
- **`estimated` precision has no storage convention**, unlike `month` and `year`. Deliberate: it means even the year is inferred.
- **No agent tools over the registry.** v1 is a service layer. When tools arrive: reads unrestricted, writes confirmation-gated `WRITE_EXECUTOR`, and `record_calving` in particular **must** be gated — it creates an animal.
